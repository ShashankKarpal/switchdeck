## 2026-08-24 (later): v1.9.1, the real notification fix, minimal bundle, identity move
- The v1.9 Info.plist-beside-the-interpreter fix was NOT sufficient, and the morning's "delivery proven" claim was wrong: the API accepted every notification and macOS filed them into Notification Center without presenting one. Evidence: deliveredNotifications listed every banner v1.9 ever posted, including real switch resume cards, while the user saw and heard nothing; the modern UserNotifications centre reported authorizationStatus denied; and com.shashank.switchdeck had no entry in notification settings at all. ROOT CAUSE: macOS only registers notification identities for real, LaunchServices-registered app bundles. An unbundled process cannot be granted banner presentation, on any macOS this project has run on.
- Ruling: minimal bundle now, full packaging still owned by the Swift rewrite. ~/Applications/SwitchDeck.app holds exactly three things: a copy of the uv-managed static CPython as the bundle executable, Info.plist, and the brand icon compiled from design/app-icons. Nothing else, because codesign rejects data files outside Resources. Stdlib and site-packages are wired through PYTHONHOME and PYTHONPATH in the LaunchAgent; ~/.switchdeck-venv still owns packages. switchdeck.py scrubs both variables from every child process so they cannot poison cswap's own interpreter (_child_env).
- Identity moved once, deliberately: com.shashank.switchdeck to com.shashankkarpal.switchdeck (the fleet's namespace). The old id carried a stale system-level denial accumulated by the unbundled era, with no entry in System Settings to flip and no way to re-prompt. The new identity prompted on first launch; granted=True is in the click log (2026-08-24T09:53:20) and survives bundle rebuilds. The launchd label stays com.shashank.switchdeck; label and bundle id are different namespaces and renaming a healthy label is churn.
- _notify order is now: modern UserNotifications centre (banner plus default sound), then legacy rumps, then osascript, with every fallback logged. request_notify_authorization runs at startup and logs the grant or denial, because a denied identity is indistinguishable from broken code without evidence.
- Verification protocol correction: "the notification API returned cleanly" and even "deliveredNotifications kept it" are NOT proof a banner was presented. Only granted modern authorization plus a human seeing the banner is proof. scripts/selftest_notify.py now exits 0 only under granted authorization, 2 when the post went out unauthorized.
- Fleet effects, same session: Content Digest got the same bundle treatment (its repo decision log has the record); xbar was uninstalled (brew cask, plugin folder removed, SwiftBar canonical, weekly widget backup task re-pointed at SwiftBarPlugins); menu-bar-swag's Restart SwitchBar.command replaced by Restart SwitchDeck.command.

## Security and hygiene rules (every agent session)

1. Never commit secrets: no API keys, tokens, passwords, private keys, or .env files. Templates belong in *.example files with placeholder values only.
2. Untracking or deleting a file does not remove it from git history. If a secret ever lands in a commit: rotate it at the provider first, then rewrite history with git filter-repo.
3. At the end of each session: delete unused code, merge duplicate helpers, remove commented-out blocks. Use deterministic tools (linters, dead-code finders) and review the diff before deleting.
4. Keep .gitignore covering .env, .env.*, and secrets.* (with !*.example exemptions). Never weaken it.
5. The gitleaks CI workflow (.github/workflows/gitleaks.yml) stays. Never remove or bypass it.

## 2026-09-05 (later): engine calls off the UI thread
- Before: refresh() ran cswap list, cswap --version and the dry-run tick synchronously on the rumps Timer, so the menu bar item froze for up to 70 s per tick when the network was down (audit 2026-09-02, B1). After: RefreshPump runs collect_snapshot() on a daemon thread and parks the result; a 1 s apply timer on the main thread takes it and renders. Every menu write stays on the main thread (AppKit menus are main-thread objects). The pump refuses to overlap a run in flight, and a worker exception is parked as a CollectError, logged, and shown as a menu row, never lost.
- Narration became a pure function, narration_outcome(rc, events, prev_key) -> (log line, notification body, next dedupe key, menu row). Side effects (click log, banner, dedupe state) run in the apply step on the main thread, so the once-per-condition guarantee is unchanged and now unit-tested (26 tests total).
- The user-initiated switch stays synchronous: the click is the moment the user is waiting, and the engine switch itself is fast; only the post-switch refresh goes through the pump.
- Startup shows a "loading..." row until the first snapshot lands instead of an empty menu.
- PROOF (2026-09-05): a second instance run through the bundle executable with a 5 s to 20 s engine wrapper and REFRESH_SECONDS 30: `sample` showed the main thread with 6 run-loop frames and 0 subprocess frames while "Thread-1 (_run)" sat in subprocess; overlapping ticks were refused without error; an engine wrapper that fails the dry run produced the main-thread click-log line "auto-dryrun error rc=1 no event" 16 s after start, proving worker to apply to log end to end.
- QUIRK: a test instance must run THROUGH the bundle executable (as scripts/selftest_notify.py documents). From the bare venv interpreter, UNUserNotificationCenter.currentNotificationCenter raises an uncaught NSException at startup and the process dies with "terminating due to uncaught exception"; that is macOS refusing an unbundled identity, not a code path this app can catch. Copy switchdeck.py beside a test local_settings.py so sys.path[0] picks the test settings.
- Audit item B2 (engine version cached) landed on 2026-09-02; B1 lands here; B8 (authorization checked only at startup) stays as is by decision, the grant is keyed to the bundle id and survives.

## 2026-09-05 (fourth): busy or idle on the live-sessions line
- The live-sessions row now says "2 live CLI session(s), 1 busy: ..." or ", idle: ...". Busy means the session's transcript file (~/.claude/projects/<encoded cwd>/<sessionId>.jsonl) was modified within SESSION_BUSY_SECONDS (10). The check is os.stat on the path; the transcript is never opened, and a test replaces builtins.open with a guard that fails on any .jsonl open to keep it that way. The resume card and the click log carry the same busy count (`live_cli=N busy=M`).
- Session record schema observed on this Mac (Claude Code 2.1.x, 2026-09-05): ~/.claude/sessions/<pid>.json with pid, sessionId, cwd, startedAt, kind, name and messaging fields; removed on exit. The project folder name is the cwd with every non-alphanumeric character replaced by '-' (so a dot becomes '-' too: /Users/me/.local -> -Users-me--local). Both are upstream conventions, not a contract; a mismatch degrades to "idle", never to an error.
- PROOF (2026-09-05): a real `claude -p` run showed {'live': 1, 'busy': 1} for its two seconds of life and {'live': 0, 'busy': 0} after exit; the idle branch is covered by a unit test with a 120 s old transcript. The stat runs inside collect_snapshot on the worker, so a large projects tree costs the main thread nothing.
- Not filtered by account (audit B5): session records carry no org, so the count is all live CLI sessions on the Mac. Correct for the warning's purpose (any live session gets the ~30 s credential lag).
- Tests: 35.
